### Phase 7a — the optional AI provider, AI report commentary, and the Support Assistant (backend)
**Upgrading:** upload the files. **No database change** (`ai_usage_logs`, `support_conversations`, `support_messages` came with migration `007`, unused until now) and **no asset rebuild** (nothing in this commit touches the compiled CSS/JS — the admin screens and the customer chat widget are the next commit of this phase).
* **One optional AI provider** ([docs/AI-AND-SUPPORT.md](AI-AND-SUPPORT.md)), off by default, configured once (owner only — `ai.configure`, not even `manager`, since this is the one decision that lets any data leave the server at all): a vendor-agnostic adapter (`App\Ai\AiProviderInterface`) with two shipped implementations (Anthropic's Messages API, and the OpenAI-compatible chat-completions shape many gateways implement), the same SSRF-guarded, pinned-resolution, byte-capped HTTP client as the SMM and payment-gateway clients, the key AES-256-GCM encrypted at rest and never returned by any API, every call recorded in `ai_usage_logs` (feature, provider, model, status, tokens, latency — **never the prompt, the answer, or the key**).
* **AI report commentary** (`POST /admin/api/reports/{date}/ai`, master prompt §6.2): sends only a small pre-aggregated summary of an already-built report (totals, deltas, service names, alert titles — never an order id, a link or a payment reference); requires strict JSON back (`summary`, `changes`, `causes`, `next_steps`, `uncertainties`, each bounded) or the reply is `invalid` and nothing is shown; stored apart from the figures (`daily_reports.ai_*`, already provisioned in Phase 6) and cleared automatically the moment a regeneration changes a number it described. Two independent switches (`ai.use_for_reports`, `ai.use_for_support`) decide which features, if any, may use the provider once it is configured.
* **The Support Assistant** (`POST /api/support/start` · `/message` · `/history`, master prompt §7): a rules-based chat that needs no AI at all. **The one rule everything else follows: a reply that carries a specific order's facts is never handed to AI.** Payment status, order status and what an expired session means come only from the exact same `Status`/`Orders::customerView()` code the order tracking page itself uses, built only from an order the customer proved they own with its 128-bit access token (the same token `/order/{token}` requires — a bare order id is refused exactly like an unrecognised token, never confirming or denying whose order a code belongs to). Only the order-free answers (where to find an order id, the refund policy, delivery times in general, payment methods, a greeting) are ever candidates for AI phrasing, and even then the model is given the already-decided answer and told only to phrase it more warmly — its reply is discarded if it is too long or invents a link. Rate-limited, length-bounded, a conversation closes itself after 200 messages, retention configurable (`support.retention_days`, purged by the existing `cleanup` job). Admin monitoring (`support.view`: owner, manager, support) and the on/off switch (`support.configure`: owner, manager) are separate from the AI decision (`ai.configure`: owner only).
* Tests: PHP **354 passed** (5,151 assertions; 3 new in `AiServiceTest.php`, 3 in `ReportAiTest.php`, 6 in `SupportAssistantTest.php`, 2 in `AiSupportAccessTest.php` — including a test that wires a fake AI provider which *would* answer an order-specific question differently, and proves the real reply never changes). **Not tested:** either AI adapter against a real provider (`api.anthropic.com` or a real OpenAI-compatible endpoint) — only against a fake implementing the same interface; their shared HTTP mechanics are the same already-proven code as the SMM/gateway clients. The admin screens and the customer-facing chat widget land in the next commit of this phase, with their own browser suites.

### Phase 6 — Business Watchdog and the daily report (Admin → Business alerts, Daily reports)
**Upgrading:** upload the files. **No database change** (the tables — `business_alerts`, `daily_reports`, `job_runs` — came with migrations `006` / `007`) and **no asset rebuild** (the compiled CSS/JS is included). With the one-minute cron line (`* * * * * php /path/to/bin/cron.php`) nothing else is needed: the two new jobs run when they are due. Hosts that use one line per job add `*/15 * * * * php /path/to/bin/cron.php watchdog` and `10 * * * * php /path/to/bin/cron.php report` ([docs/OPERATIONS.md](docs/OPERATIONS.md)).
* **Business Watchdog** ([docs/WATCHDOG-AND-REPORTS.md](docs/WATCHDOG-AND-REPORTS.md)): twelve health checks over the shop's own records, every 15 minutes — failing payments, rejected / unprocessed / repeated gateway notifications, SMM provider call errors, stuck paid orders, a rise in the provider's final cost per 1,000, services and orders with no cost, a drop in verified sales, a change in conversion, scheduled jobs that fail or stopped, errors in the application log, money that does not add up (revenue without a verified payment, a differing paid amount, a refund mismatch) and — **off by default** — the provider's balance. Eight are fixed rules; three are comparisons with recent history and are labelled **heuristic**; none is an AI. Thirty thresholds are editable within hard limits and every change is audited with before and after.
* **It does not guess:** a check with too little history or an answer it cannot get says *not enough data* / *could not be asked* — never *OK* — and neither raises nor closes an alert. **One alert per problem** (a unique index): a repeat detection counts up, severity only escalates; an alert is resolved by the watchdog only after the check has run clean *n* times in a row (default 2), and a switched-off check never closes its own alert in silence. *Acknowledge* keeps an alert live (who and when are kept); *Resolve* asks first, and if the problem is still there the next run opens a **new** alert. **Dry run** shows what the checks would do and writes nothing.
* **Admin → Overview → Business alerts:** four cards (critical, warnings, not acknowledged, last check), tabs *Alerts* (filters by status, severity and kind), *Checks* (what each check last saw, its type, its numbers), *Thresholds* (every setting with unit, bounds and default; a bad value is refused in place) and *E-mail*; **Run checks now** and **Dry run**; a sidebar badge (amber, red while a critical alert is unseen) and a **dashboard card** with the worst alerts. Optional **alert e-mail** (off by default; ≤ 5 recipients; minimum severity and cooldown; no credentials or customer data in it; PHP `mail()` can only say it *handed the message to the mail system* — the page never says "delivered").
* **Daily report** ([docs/WATCHDOG-AND-REPORTS.md](docs/WATCHDOG-AND-REPORTS.md)): one report for every **finished** business day (Asia/Kolkata, midnight to midnight), written once by the `report` job shortly after 00:10 IST (it also catches up days it missed, at most 7 per run) or by an admin — **one row per day** (a unique index; a second run creates nothing). Integers only, calculated from the source tables by the same code as the dashboard and Finance: sales, orders by where they are now, payments, costs, profit, visitors, the day compared with the day before, most profitable / loss-making services and the ones that **sold with an unknown cost**, API and payment failures, the alerts open when it was built and a few plain sentences written by fixed rules. **Every figure carries a basis — measured, estimated, incomplete or unavailable** — with a note; an unknown cost is never silently ₹0. *Regenerate* rebuilds a day **in place** and audits which figures changed. No AI wrote any of it (the AI columns stay empty until the optional AI step of a later phase).
* **Admin → Overview → Daily reports:** the history (filters by date, 20 per page, days with no report announced and creatable from the page), a full report with its notes, comparison and definitions, **Regenerate** (asks first).
* **System → Scheduled jobs:** every job's state (*on schedule / overdue / failing / never run*), last run, last success and failures in 24 h, with **Run now** and **Dry run** (a job without a dry run has no such button; the server answers `422` if asked). `docs/OPERATIONS.md` lists the jobs, the cron lines and what each guarantees.
* **Roles, enforced on the server:** every role reads alerts (`alerts.view`); acknowledging, resolving and changing thresholds or the e-mail needs `alerts.manage` (owner, manager); reports contain profit, so `reports.view` is owner, manager and analyst — **not support** — and `reports.generate` is owner and manager.
* **Fixed along the way:** an alert description was cut at 300 characters, mid-sentence (it now keeps 1,000, still cleaned of paths and tokens); the dashboard headings *Profit & trends* / *Revenue & profit* showed a literal `&AMP;` (a Phase 5a bug); the dashboard's "Full profit statement" link was a 20 px tap target; the security audit's route sampler could not build a date-shaped route parameter; two screen-reader landmarks shared a name on the System page; the QA "nothing covers a control" check now understands a sticky save bar (it passes only when scrolling brings the control out from under it).
* Tests: PHP **340 passed** (5,007 assertions; 25 new in `WatchdogTest.php`, 15 in `DailyReportTest.php`, 3 in `AlertsAccessTest.php`, the job / cron / alert tests in `OpsTest.php` extended); browser suites `admin-alerts` **19/19** (a real watchdog run over planted problems, every row and card against independent SQL, filters, acknowledge / resolve / recurrence, run now and a dry run, the Checks and Thresholds tabs, a switched-off check, e-mail settings, the dashboard card and menu badge, every role, a phone) and `admin-reports` **13/13** (every tile against the raw records, basis labels and notes, the comparison, deep links, a missing day created from the page, regenerate in place with its audit, every role, a phone). The regression suites for everything that changed (`admin-*`, `a11y`, `security-audit`, `perf`) were re-run — see [docs/QA-REPORT.md](docs/QA-REPORT.md). **Not tested:** a live Alpha UPI account or SMM panel (mocks only — Alpha UPI reports no fee, so payment fees stay estimates; there is no gateway "health" call to poll), real mail delivery (`mail()` was replaced by a recorder), the provider-balance check against a real provider (it uses the documented `balance` call and is off by default); the MySQL 8 run of the new tests is part of the final pass.

### Phase 4 — order recovery (safe retries, the queue, reconcile actions)
**Upgrading:** upload the files. No database change (the columns it uses came with migration `006`) and no asset rebuild (the compiled CSS/JS is included). Add the cron line `*/5 * * * * php /path/to/bin/cron.php recovery` (or keep the one-minute `php bin/cron.php`; it runs the job when due).
* **Order recovery** (Admin → Sales → *Order recovery*, [docs/ORDER-RECOVERY.md](docs/ORDER-RECOVERY.md)): every paid order that is not where it should be, derived live from the orders (nothing stored that can go stale): *provider outcome unknown*, *needs review*, *failed*, *sending is stuck*, *repeated provider errors*, *provider not followed*, *waiting to be sent*, *retry scheduled* — with the reason, attempts (*n of max*), last / next attempt, the provider order and status, and the safe next action. Cards, filters with counts, search, a sidebar badge, a *What the problems mean* legend, a retry-policy tab, **Run recovery now** and **Dry run**; the Orders drawer shows a *Recovery* section and offers the same actions.
* **The rule it is built around:** the SMM API v2 has **no idempotency key and no lookup by link**, so an order whose outcome nobody can know is **never resent by itself**. A person looks in the provider's panel and either **links** the order that is there (the provider's own `status` call must know the id; never linked to two orders — a named lock) or **resends after checking** (they type CHECKED and say what they looked at; the server refuses `422 verification_required` without the statement and a note). Automatic retries are only for "the provider could not be reached, nothing was sent": 60 s → 5 min → 20 min → 1 h, up to a configurable maximum (1–10, default 5), then a person is asked.
* **Actions** (permission `orders.recover`: owner, manager — enforced on the server, also through the Orders drawer): *Send now* (re-reads the service so a corrected SMM id applies; the claim lock makes a double click send once), *Resend after checking…*, *Link provider order…*, *Move to manual queue…*, *Sync*, *Mark for review*, *Escalate* (who and when kept, note required), *Resolve* (note required). Each is checked against the order's state (`409 not_allowed`), idempotent per click, written to the order's timeline and the audit log.
* **The `recovery` job** (`php bin/cron.php recovery [--dry-run]`, per-job lock, time budget, run history): hands over orders whose sending was interrupted (never resends them), sends due orders (a person's *needs review / escalated* mark pauses an order), follows live provider orders, tidies the marks. *Dry run* reports what it would do and changes nothing. `GET /admin/api/jobs` and `POST /admin/api/jobs/{job}/run` (permission `jobs.run`, 10 per 10 minutes, audited) are the first routes of the scheduled-jobs health screen that arrives in a later phase.
* **Also:** *Approve All* now leaves out a paid order whose payment has an open **high** payment flag (and says how many it held back); the order failure message no longer has a doubled full stop; the admin order drawer says *Send now* / *Resend after checking…* instead of *Retry provider submission*.
* Tests: PHP **259 passed** (3,901 assertions; 19 new in `RecoveryTest.php`); browser suite `admin-recovery` **27/27** (orders put into every state, numbers = the database, every action and refusal, double click sends once, Dry run changes nothing, retry policy, drawer, axe, keyboard, 1440 / 1366 / 1100 / 820 / 390 px, role matrix). Not tested: a live SMM panel (mock only).

### Phase 3 — payment checks (verification, idempotency, fraud flags)
**Upgrading:** upload the files, then **Admin → System → Apply database updates** (or `php bin/migrate.php`) — migration `010_webhook_duplicates` adds one nullable column (`webhook_events.last_attempt_at`). Nothing else in the payment path changes shape: the amount / currency / one-time-reference / row-lock rules that protect money are the same.
* **Payment checks** (Admin → Sales → *Payment checks*, [docs/PAYMENT-CHECKS.md](docs/PAYMENT-CHECKS.md)): a monitor of every payment — expected vs verified amount, currency, state in the requested vocabulary (`CREATED · PENDING · PAID · FAILED · EXPIRED · REVIEW_REQUIRED · REFUNDED`), verification source, created / verified / expiry times, flags and webhook status — a flags list, and the thresholds. Safe reconciliation: **Re-check** (asks the gateway about one payment; settles/fails/expires an unpaid one by the poll's own rules, never releases a held one), **Reviewed / False alarm** (who, when, why), and the owner-only manual confirmation (audited, recorded as a person's decision, never as a gateway confirmation).
* **Flags, not punishments** (`App\Services\Risk`): amount mismatch, currency not INR, amount not reported, reused bank reference, paid more than once, paid after the session ended, unknown order reference, gateway answers disagree (webhook vs lookup), webhook signatures failing, repeated unfinished payments, order/payment records that disagree. One live flag per problem (unique index), occurrences counted, facts kept without payloads or secrets, configurable thresholds with limits. A **high** flag also raises a critical Business Watchdog alert (e-mail optional, off by default, sent after the transaction commits). Nothing blocks a customer, cancels an order or moves money.
* **Cross-check of webhooks** (`risk.webhook_double_check`): `off`, `flag` (default — credit on the signed webhook, then ask the gateway after the response and flag a disagreement; a "not paid yet" answer is flagged only after a grace period) or `require` (credit only from our own lookup; a gateway that cannot be asked gets a `503` and delivers again). The old admin text that claimed every payment was "double-checked" was inaccurate for webhooks and has been corrected.
* **Duplicate deliveries are audited:** repeats are acknowledged and counted on the original event (`attempts`, `last_attempt_at`) and shown on the screen; the dedupe strategy for a gateway without event ids (SHA-256 of the body) is documented.
* **Scheduled:** the `payments` job now also runs the risk scan (bursts of rejected signatures, repeated unfinished payments, records that disagree, the cross-check backlog, auto-closing flags whose condition is gone); `--dry-run` writes nothing and asks the gateway nothing.
* **Roles are enforced on the existing admin pages and API** (`403 forbidden`): `manager` runs the shop but cannot confirm a payment by hand or open the gateway / SMM settings; `support` and `analyst` are read-only; the navigation and the order drawer only offer what a role may do. Every existing admin is an `owner`, so nothing changes until a role is assigned (`php bin/admin.php role …`). New permission `audit.view`.
* Tests: PHP **240 passed** (3,730 assertions; 28 new in `RiskTest.php`); browser suite `admin-checks` **19/19** (monitor, filters, re-check, cron scan, review / dismiss, thresholds, axe, keyboard, phone / tablet, role matrix).

## Payment page: the real QR, directly in the card (this release)

**Upgrading:** upload the files. No database change (migration `004` from the previous release is still the latest) and no asset rebuild (the compiled CSS/JS is included).

**What was wrong.** The previous release stopped drawing a QR of the gateway's hosted-checkout URL (a UPI app cannot pay an https address, and a camera opens it as a page that draws *another* QR) — but replaced it with an instruction card: *"open the secure payment page in a new tab and scan a second QR"*. That is not the experience wanted. The customer should scan **one** QR, on **our** page.

### The payment page
* **SOCIAL MEDIA BOOSTER → SECURE PAYMENT → PAY SECURELY → `₹5 — 50 Followers`** and one centred white card (rounded, subtle border, premium shadow): **SCAN AND PAY**, **the order's own QR** (up to 20 rem wide, high-contrast, quiet zone — scannable from another phone), the payee, **DOWNLOAD QR CODE** directly below it, and **TIME LEFT TO PAY 05:00** under that. Phones also get **OPEN UPI APP** (a phone cannot scan its own screen). The glassmorphism, logo, fonts and colours are unchanged.
* **Gone:** the instruction card ("You finish paying on our payment partner's secure page…", "Tap PAY ₹5 NOW. The secure payment page opens in a new tab", "scan its QR code…"), the **PAY ₹X NOW** button and the second-page workflow.
* **DOWNLOAD QR CODE** saves the very QR on screen (`GET /pay/{ref}/qr.png?download=1`, `SMB-XXXXXXXX-payment-qr.png` — the order id), not a screenshot of the page.
* The 05:00 countdown is still computed from the server's clock and sits under the QR; at 00:00 the QR, the download and the app button die and the page says *Payment session expired*.

### Where the QR comes from
* **What Alpha UPI documents** is a hosted checkout URL (`create-order` → `data.payment_url`) and nothing else — no QR image, no Base64, no QR payload, no UPI URI (the bundled SDK returns the same URL only). So there is nothing documented to "just display".
* **What the server now does:** it opens that documented `payment_url` itself (no credentials sent, the gateway's own host only, SSRF-guarded, 5 s, 600 KB), finds the `upi://pay?…` request the page's QR is made of, accepts it **only** if it is for exactly this order's amount in INR with a valid payee and known parameters, stores it with the payment, and draws the QR with its own PNG encoder. A QR of the https URL is never drawn. Every page view and every image request re-validates it against the payment's own amount.
* **When the page carries no usable request** (or the lookup is switched off, or the page is down), checkout sends the browser **straight to the gateway's own checkout page** in the same tab — the documented "redirect your customer to `payment_url`" — instead of an instruction card; our `/pay/{ref}` page then degrades to a slim **COMPLETE YOUR PAYMENT** card with the timer and one **CONTINUE TO PAYMENT** button.
* **Verification is unchanged and server-side only:** signed webhook or the server's own `check-status`; a view, a scan, a download or a click never marks anything paid; the exact amount, INR, a one-time UTR, duplicate webhooks, unknown orders, failed and expired sessions behave as before.

### Admin
* **Payment gateway → Check QR support:** asks first, creates one ₹1 test order at the gateway (never paid, not one of your orders) and says in words whether its checkout page carried a usable UPI request, and why not if it did not. Rate-limited, idempotent, audited (`gateway.qr_checked`).
* **Show the gateway's QR on my payment page** (default on): switch the lookup off to send every customer straight to the gateway's checkout.
* The local demo's fake gateway has a **fake bank** page at <http://127.0.0.1:4010/> to "pay" an order after its QR is shown.

### What this does **not** guarantee
* Reading a QR out of the gateway's checkout page is **not a documented API**. It works only while that page carries the UPI request in a readable form, and may stop working if the gateway changes it.
* **Not tested against the live gateway** (`alphaupi.site` was unreachable from the build machine) **and no real UPI payment was made.** The tests use a protocol-faithful mock whose page carries the request in several forms and, for the fallback, none. Use **Check QR support** on your server for the real answer.
* For a QR on your own page regardless of the gateway's page, you need a gateway (or an Alpha UPI plan) whose API returns the UPI request — ask Alpha UPI support, or add an adapter with `Gateways::register()` that sets `CreatePaymentResult::$upiIntent`.

### The service-link input (same release)
* **What was wrong:** the field auto-focuses when a card opens, and its focus state stacked a 4 px pink ring on a pink border inside a card that already had its own pink outline — a thick, glowing double border, worst on phones. A tap also left the hover colour behind.
* **Now:** one **1.5 px pink border** on a white field (the browser renders it as 3 physical pixels at 2× density, 4 at 3×, 1 on a 1× screen, where half pixels do not exist), **no shadow** at rest, and when focused **one soft 2 px ring** (the border deepens slightly; nothing is added to the wrapper, the form or the card; no layout shift). Valid / invalid use the same single border + 2 px ring in green / red; disabled is a quiet grey. Hover emphasis exists only on devices that can hover. The placeholder stays clear of the link icon and is cut with an ellipsis; the dark premium card's field is white too. The change is scoped to the storefront link field (`.input-wrap > .input`); admin inputs are untouched.
* **Verified on the rendered page** by a new suite, `tools/qa/site-input.mjs` (12 steps): a 360×800 Android phone (2×), a 390×844 iOS-sized phone (3×), a 768×1024 tablet (2×) and a 1440×900 desktop (1×), in a normal and in the dark premium card — border width and colour, thickness read from the screenshot pixels, exactly one shadow, no outline, wrapper / form / card unchanged, no layout shift, no overflow, a Tab-reachable focus indicator.

### Small phones
* The payment card overflowed a 360 px wide screen by 11 px (a grid item's natural width, found by the layout suite). The card may now shrink, and the paddings are a little tighter below 400 px so the QR stays large.

## Account links, INR only, and the payment QR (previous release)

**Upgrading:** upload the files, then **Admin → System → Apply database updates** (or `php bin/migrate.php`) to apply migration `004` — it only replaces the *old default* payment-page instructions text, never a text you wrote. Rebuilding assets is not needed (the compiled CSS/JS is included).

### Followers and Subscribers ask for the account link
* **Instagram Followers** → label **Instagram Profile Link**, placeholder `https://www.instagram.com/username/`. **YouTube Subscribers** → **YouTube Channel Link**, placeholder `https://www.youtube.com/@channelname`.
* No username or `@handle` is asked or accepted for these two. Accepted: `instagram.com/<name>` (with or without `https://`, `www.`, `m.`, a trailing slash, tracking parameters, `/_u/<name>`); `youtube.com/@handle`, `/channel/UC…`, `/c/<name>`, `/user/<name>`, a legacy `/<name>`. Refused: other domains and look-alikes (`instagram.com.evil.com`, credentials, odd ports, `ftp:`/`javascript:`), post / video links, the site root, malformed names.
* Validated live in the browser **and** again on the server (the server's answer is the one that counts; both run the same 219 fixture cases). The order keeps the complete validated link; the SMM panel receives it; the admin Orders list, drawer and **Manual delivery** section show it with *open* and *copy*; the customer's tracking page and "Your orders" drawer show it; the order history line carries it.
* Blue Tick, likes, views and watch time keep their current inputs.

### INR only
* The SMM provider form no longer has a currency (it defaulted to **USD** and offered INR / USD / EUR / GBP) or an exchange rate. A provider's charge is read as rupees; a charge a panel declares in another currency is **not converted** — the ₹ cost you enter on the service stays in force — and *Test connection* says when a panel bills in another currency. The dashboard's dollar-sign icon is now a rupee badge.
* A gateway that opens an order in another currency is refused; a success it reports in another currency is held for review and never fulfilled. Amounts are sent to the gateway as rupees with two decimals (`5.00`).
* Database defaults were already INR; nothing in the database is rewritten (the two legacy provider columns are set to `INR` / `1.0` only when you save that provider).

### Payment QR *(the card described here was replaced by the release above)*
* **Root cause:** the QR encoded the gateway's *hosted checkout URL*. A UPI app cannot pay an https URL and a camera opens it as a web page that draws another QR. The documented Alpha UPI API (and the bundled SDK) returns only that URL — no UPI request, QR string or image.
* The payment page draws a QR **only** for a real `upi://pay` request for exactly this order and amount (INR, valid payee, no repeated or unknown parameters), re-checked on every view and every `qr.png` request. *(That release then showed a hosted-checkout instruction card for Alpha UPI — removed in the release above, which reads the request from the gateway's own checkout page instead.)*
* Payments created before the fix are shown as hosted checkouts. The default payment instructions no longer promise a camera scan that opens a page.
